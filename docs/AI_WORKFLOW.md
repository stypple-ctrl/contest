# AI 작업 흐름: 이 저장소의 데이터 파이프라인 스킬

이 문서는 현재 저장소에 포함된 `.agents/skills/contest-*` 절차를 설명한다. 특정 AI 플러그인이나 모델이 실제로 사용되어 효과를 냈다고 주장하지 않는다. 여기서 말하는 효과는 **스킬에 적힌 책임 분리와 점검 규칙을 따르면 기대할 수 있는 운영상 이점**이다.

## 전체 흐름

```text
후보 수집 → 표준화 → 교차 검수 → SQLite 적재·검색
 collecting    normalizing    verifying       data-service
                         \---- contest-harvest가 순서 조율 ----/
```

`contest-harvest`는 위 단계를 조율하는 안내서다. 실제 외부 크롤링은 트래픽과 약관 문제를 일으킬 수 있으므로, 이 스킬은 첫 실행 전에 대상 사이트와 범위에 대한 사용자 승인을 요구한다.

## 스킬별 역할과 사용 시점

| 스킬 | 맡는 일 | 도움이 되는 이유 | 한계 | 추천 시점 |
|---|---|---|---|---|
| `contest-collecting` | 사이트 목록·상세 페이지에서 원문과 출처를 수집 | 해석을 뒤 단계로 미뤄 원본 대조 가능성을 남긴다 | robots·이용약관을 무시해도 되는 권한을 주지 않으며, 수집 누락도 자동으로 알 수 없다 | 새 출처를 추가하거나 특정 출처를 재수집할 때 |
| `contest-normalizing` | 학년, 지역, 날짜, 분야를 표준 레코드로 변환하고 요약을 재작성 | 서로 다른 표현을 검색 가능한 값으로 맞추고 원문 필드를 남긴다 | 애매한 참가 자격을 사실처럼 확정할 수 없다 | 원시 데이터를 검색·DB에 넣기 전 |
| `contest-verifying` | 필수값·날짜 논리·중복·원본과의 차이를 점검 | “필드가 채워짐”을 넘어 원본과 표준값을 비교하게 한다 | 원본을 다시 확인하지 못한 레코드는 verified가 될 수 없다 | 정규화 배치마다, 또는 conflict를 재확인할 때 |
| `contest-data-service` | 검수 레코드를 멱등 upsert하고 검색 UI의 기본 축을 정함 | 재실행해도 중복을 줄이고, 학년·지역·마감일 검색을 중심에 둔다 | SQLite MVP가 대규모 동시접속이나 모든 운영 요구를 해결하지는 않는다 | 검수 결과를 서비스 데이터로 반영할 때 |
| `contest-harvest` | 네 단계를 순서대로 연결하고 중간 산출물·보고를 관리 | 단계별 책임과 실패·충돌 보고를 한 흐름으로 유지한다 | 실제 데이터 품질은 각 단계의 입력, 원본 접근성, 사람의 판단에 달렸다 | 전체 갱신, 증분 갱신, 또는 일부 단계 재실행을 계획할 때 |

## 효과적으로 쓰는 순서

1. **수집 전에는 범위를 정한다.** 대상 사이트, 학생 연령, 기간, 요청 빈도를 먼저 합의한다.
2. **수집 단계에서는 판단하지 않는다.** 제목·URL·참가 조건·날짜의 원문을 보존한다.
3. **정규화 단계에서만 검색용 값으로 바꾼다.** 변환 불가 값은 비워 두거나 conflict로 보낸다.
4. **검수 단계에서 원본을 다시 대조한다.** 특히 참가 자격과 마감일을 우선한다.
5. **검수 결과만 적재한다.** 적재 후에는 만료 상태를 갱신하고, 사용자에게는 원본 공고 링크를 제공한다.

## AI를 쓸 때도 남는 사람의 책임

스킬은 판단을 구조화할 뿐, 다음 결정을 대신하지 않는다.

- 크롤링 대상 사이트의 robots.txt·이용약관 준수 여부
- 모호한 “청소년”, “일반인 포함” 조건의 최종 해석
- 원본 링크가 실제 공식 공고인지 판단
- conflict 항목을 서비스에 어느 범위까지 노출할지 결정
- 자동 갱신을 실행할 권한과 API 키 관리

좋은 요청은 결과만 요구하지 않고 근거와 보류 항목을 요구한다. 예를 들어 “이번 주에 새로 열린 초·중·고 대상 공모전을 수집하되, 원본 링크와 마감일을 확인할 수 없는 항목은 conflict 목록으로 따로 보여 달라”고 요청하면, AI와 사람이 나눠 맡을 경계가 분명해진다.
