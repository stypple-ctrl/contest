# 다른 주제의 검색 서비스로 응용하기

이 저장소는 “공개 정보에서 후보를 찾고, 확인 가능한 형태로 정리한 뒤, 가벼운 검색 화면으로 보여 주는” 구조의 예시입니다. 공모전 대신 지역 체험, 도서관 프로그램, 장학금, 교육 자료처럼 다른 주제로 바꿀 수 있습니다. 다만 이름만 바꾸기보다 데이터 기준과 확인 방법을 먼저 정해야 합니다.

## 가장 안전한 시작점

처음에는 전체 수집기를 바꾸지 말고 `web/`을 복사해 **고정된 작은 데이터 스냅샷**으로 화면부터 바꾸는 편이 좋습니다.

1. 새 주제에 필요한 검색 질문을 한 문장으로 씁니다. 예: “학부모가 지역과 날짜로 어린이 체험을 찾는다.”
2. `web/src/types/contest.ts` 또는 `web/src/types/culture.ts`를 참고해 새 항목의 자료형을 정합니다.
3. `web/src/lib/contest-data.ts` 또는 `web/src/lib/culture-data.ts`의 예시 데이터를 새 자료로 바꿉니다.
4. `web/src/components/`의 필터·카드 문구를 새 주제에 맞춥니다.
5. `npm run lint`, 관련 테스트, `npm run build`로 화면이 깨지지 않는지 확인합니다.

이 단계만으로도 기존 홈페이지, DB, API 키 없이 독립 실행되는 학습용 프로토타입을 만들 수 있습니다. 데이터 파일은 정적 스냅샷이므로 바뀐 정보를 자동으로 가져오지는 않습니다.

## 데이터 설계: 먼저 결정할 것

새 주제마다 아래 네 가지를 문서로 먼저 합의하세요.

| 질문 | 예시 |
| --- | --- |
| 사용자가 거를 기준은 무엇인가? | 지역, 대상 연령, 날짜, 가격, 분야 |
| 반드시 있어야 하는 정보는 무엇인가? | 제목, 원본 URL, 일정, 운영기관 |
| 무엇을 원문 그대로 보관할 것인가? | 출처 URL, 대상·일정 원문, 수집 시각 |
| 무엇을 추정하지 않을 것인가? | 연령 적합성, 마감일, 무료 여부 |

공모전 구조를 그대로 쓴다면 `source_url`은 후보를 발견한 페이지, `official_url`은 기관의 원본 안내 페이지로 구분하는 원칙이 유용합니다. 사용자에게는 가능한 한 원본 URL을 보여 주고, 집계 페이지 URL은 감사·재확인용으로 남기세요.

## 갱신 가능한 서비스로 확장하기

고정 데이터 화면이 안정된 뒤에만 전체 저장소의 파이프라인을 바꾸는 것을 권합니다.

```text
새 공개 출처 또는 API
  → 수집 스크립트
  → 표준 레코드로 정규화
  → 필수값·날짜·출처 검수
  → SQLite 저장
  → web/src/lib/*-data.ts로 내보내기
  → Next.js 빌드
```

현재 프로젝트에서 역할별 참고 위치는 다음과 같습니다.

- 수집: `scripts/collect_contest_sources.py`, `scripts/collect_kopis_culture.py`, `scripts/collect_cultureinfo.py`, `scripts/collect_kcisa_museum.py`
- 정규화·공모전 DB 적재: `scripts/normalize_multi_contests.py`
- 검수: `scripts/verify_contest_cross_sources.py`, `scripts/verify_culture_cross_sources.py`, `scripts/live_check_urls.py`
- 웹 데이터 내보내기: `scripts/export_web_data.py`, `scripts/export_culture_web_data.py`
- DB 초기화: `scripts/init_culture_db.py`

새 필드를 추가한다면 DB, 내보내기 스크립트, TypeScript 타입, 화면을 함께 바꿔야 합니다. 한 곳만 바꾸면 데이터가 사라지거나 화면과 타입이 어긋날 수 있습니다. 공모전 필드를 확장할 때는 `.agents/skills/contest-normalizing/references/record-schema.md`가 기준 문서입니다.

## 출처와 운영에서 지킬 선

- 출처 사이트의 요약문을 그대로 재게시하지 말고, 필요한 사실을 확인해 자체 문장으로 요약합니다.
- robots 규칙, 이용약관, API 사용 조건을 수집 전에 확인합니다.
- 사이트가 차단하거나 허용 범위가 불명확하면 수집을 계속하지 않습니다.
- API 키는 `.env` 또는 `.env.local`에만 두고 Git에 올리지 않습니다.
- 외부 이미지, 로고, 원문 페이지에는 각 원출처의 권리가 적용될 수 있습니다.
- 검수 상태가 낮거나 일정이 불명확한 항목은 확정 정보처럼 추천하지 않습니다.

## 언제 서버를 추가할까

현재 방식은 한 번 생성한 TypeScript 파일을 웹앱이 읽으므로 단순하고 배포가 쉽습니다. 다음 요구가 생기면 API와 서버형 DB를 별도 설계할 시점입니다.

- 여러 사람이 동시에 데이터를 수정해야 한다.
- 매시간처럼 자주 최신 데이터가 필요하다.
- 로그인, 권한, 개인별 저장 목록 동기화가 필요하다.
- 데이터가 커져서 정적 번들로 전달하기 어렵다.

서버를 추가해도 수집 → 정규화 → 검수 → 저장이라는 순서는 유지하는 편이 안전합니다. 화면을 먼저 만들고 데이터 품질 기준을 고정한 뒤, 실제 운영 요구가 생겼을 때 확장하세요.
